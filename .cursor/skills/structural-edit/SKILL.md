# Structural Edit

A structural edit, also called a developmental edit, asks one question: does the shape of this piece match its own ambition. It doesn't ask whether the prose is clean — that's proofreading's job. It doesn't ask whether it sounds like the author — that's voice work. It asks whether the piece, as organized, actually delivers on what it set out to do.

This skill produces a report, not a rewrite. It tells the writer what's structurally wrong and why, in plain terms, and ends with a verdict on what kind of revision the piece actually needs. If the writer then asks for the restructure itself, hand off to whatever voice or composition skill applies — this skill's job ends at the diagnosis.

## Before anything else

Read the entire piece once, straight through, before evaluating any part of it. Structural problems are often invisible until you've seen the whole arc — a frame that gets dropped, a claim that gets buried, an ending that was earned three paragraphs early. You can't see any of that from a partial read.

When the draft is a Google Doc or Drive file, read it with the Google Drive tools. When it is a local file, read the file. Do not ask the user to paste the whole piece if a path or URL is already available.

## The checks

Run every finished draft against all nine of these. Not all nine will find something in every piece — say so plainly when a check comes back clean, don't pad the report to make every category look productive.

**1. Frame integrity.** Does the piece announce an organizing device in its opening — a metaphor, a question, a structural promise — and carry it all the way through? A device set up in paragraph one and abandoned by paragraph four is one of the most common failures in a first full draft, because the device is often what got the writer started, and gets left behind once the real material shows up. Note exactly where it appears and where it should have returned but didn't.

**2. Open loops.** Flag every place the draft defers something — "that's another story," "I'll get into that another time," "more on this later" — without ever paying it off. One deferred thread, used on purpose, is a real technique: a door left open. Three or four in one piece reads as a writer noticing good material and declining to use it, which lands as evasion even when it isn't. Count them. If there's more than one or two, say so.

**3. Redundant passes.** Does the piece discover or state the same insight more than once without deepening it each time? Circling an idea two or three times on the way to the final version is normal mid-draft thinking. In a finished piece, only the strongest pass should survive — the others get cut to a single sentence or folded into it. Name which pass is strongest and why, not just that repetition exists.

**4. The load-bearing claim.** Every piece has one idea doing the most work — the thing that actually resolves whatever tension the piece set up. Find it, and check where it's positioned. If it's the real hinge of the piece, it needs to read like one: given space, marked as a turn, not dropped mid-paragraph as an aside on the way to something else. Say explicitly what the claim is and why it's the one carrying the piece, not just that "something feels buried."

**5. Grounding for direct claims.** Anywhere the writer leans on an outside source to justify a claim — a text, a quote, a statistic, a scripture reference — check whether that source is actually cited. A piece that argues "I know this because the source said so" without ever pointing at the source undercuts its own authority. This generalizes past scripture: any borrowed authority that goes uncredited is a structural gap, not a style choice.

**6. Self-correction that doesn't resolve.** Visible self-correction ("I mean," restating a claim more precisely) is often a feature, not a bug, especially in a spoken or dictated voice. But some corrections still leave the sentence unclear even after the correction lands. Flag those specifically — this is different from a grammar note, because the fix isn't mechanical, it's that the thought needs one more pass before a reader can follow it.

**7. Ending mechanics.** Identify the strongest possible closing line already present somewhere in the draft — it's almost always already there, usually a paragraph or two before the actual end. Then check what sits between that line and the real ending. If later material dilutes momentum instead of building it, say so and name what should move earlier or get cut.

**8. Benchmark passage.** Find the single best-written paragraph or sentence in the draft — the one sharper and more exact than anything around it. Name it explicitly and quote it. This gives the writer a concrete standard ("make the rest of it as good as this already is") instead of an abstract one ("tighten this up").

**9. Protected material.** Identify what's already working, usually the most concrete and least explained passage in the piece, and say explicitly that it should survive revision untouched. A structural edit that only lists problems risks getting the strongest material smoothed away during the fix.

## Delivering the report

Hold nothing back. Lead with the real problems, not a compliment sandwich — state a genuine strength when you find one, but don't open with it to soften what follows. Quote the actual lines you're critiquing rather than paraphrasing them, so the writer can see exactly what triggered the note.

Write it as direct address to the writer, second person, plain prose. No headers, no bullet points, no numbered list markers in the delivered report — the nine checks above are your internal checklist, not a structure to expose verbatim in the output. Organize the report as flowing paragraphs, roughly one per finding, in whatever order tells the piece's story best (usually frame problems first, since they affect how everything else reads).

Match whatever format or voice preferences the user has already stated for their own writing — if they've told you to avoid markdown, dashes, certain words, or particular rhetorical patterns in their own prose, apply those same constraints to the report you write about their prose.

## The verdict

Every report ends with an explicit call: is this a sentence-level revision, or does it need a structural rewrite. Say which, and say why in one line. If it's structural, name the fork in the road plainly — the two or three real shapes the piece could take — rather than picking one for the writer. Let them choose the direction; that choice is theirs.

Then stop. Don't restructure the piece unless asked. This skill's output is the diagnosis and, if useful, the fork in the road — not the rewrite.

## After the verdict

If the writer picks a direction and asks for the actual restructure, that's a different job — hand off to whatever skill composes or revises in the writer's voice (for this user, [steve-voice](../steve-voice/SKILL.md) when available). If the writer instead asks for a mechanical pass — spelling, grammar, paragraph splits — hand off to [proofreading](../proofreading/SKILL.md). This skill's report can note structural issues, but per proofreading's own scope, it doesn't fix them.

## Relationship to other skills

Grilling stress-tests an idea before a draft exists — it happens upstream of this skill. This skill runs once a real draft exists. Proofreading runs downstream, after structure is settled, catching what structure work doesn't touch. Voice work (steve-voice, for this user) can run either alongside a structural rewrite or after one, once the shape is decided.

**Order:** grill the idea → draft it → structural-edit the draft → decide the shape → then voice and proofread the result.

On a full draft where the user has not specified edit type, run this skill first. Do not jump to proofreading or steve-voice until the structural verdict is clear (or the user explicitly asks for those passes only).
